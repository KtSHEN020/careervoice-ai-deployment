# CareerVoice AI Orchestrator

Repo 4 of the **CareerVoice AI** portfolio project.

## Purpose

This repository connects the existing CareerVoice AI repositories into one runnable local workflow.

The expanded MVP workflow is:

```text
profile, text, or voice input
→ career_profile.json
→ resolve job search queries
→ jobs.json
→ recommendations.json
```

The orchestrator coordinates the other repositories through their command-line interfaces. It does not duplicate their internal extraction, collection, or recommendation logic.

## Project Suite

CareerVoice AI is a multi-repository portfolio project for turning user career preferences into explainable job recommendations.

### Repo 1: voice-career-profile-extractor

```text
voice or text input
→ structured career_profile.json
```

Repo 1 supports:

- text input
- voice-to-text input
- rule-based profile extraction
- LLM-assisted profile extraction

### Repo 2: preference-aware-job-recommender

```text
career_profile.json + jobs.json
→ ranked job recommendations with explainable scores
```

Repo 2 supports:

- rule-based job scoring
- LLM-assisted job scoring
- explainable recommendation output

### Repo 3: job-listing-collector

```text
one or more job search queries
→ collect job listings
→ normalize jobs
→ deduplicate jobs
→ export jobs.json
```

Repo 3 currently supports:

- Adzuna source adapter
- repeated job search queries
- environment-based API configuration
- rule-based normalization
- cross-query deduplication
- JSON export
- CLI usage

### Repo 4: careervoice-ai-orchestrator

```text
profile, text, or voice input
→ career profile extraction when needed
→ automatic or explicit query resolution
→ job collection
→ recommendation scoring
→ final outputs
```

Repo 4 connects the previous repositories into one local command-line workflow.

## Current MVP Scope

The current MVP focuses on local command-line orchestration.

It supports three input modes:

```text
--input-mode profile
--input-mode text
--input-mode voice
```

It also supports:

```text
--profile-extractor rules
--profile-extractor llm

--scorer rules
--scorer llm
```

### Profile mode

Profile mode starts from an existing `career_profile.json`.

```text
existing career_profile.json
→ resolve job queries
→ Repo 3 collects jobs.json
→ Repo 2 generates recommendations.json
```

This mode is useful when a career profile has already been created manually or generated by Repo 1.

### Text mode

Text mode lets the user type career preferences directly in the terminal.

```text
terminal text input
→ Repo 1 generates career_profile.json
→ Repo 4 reads target_roles
→ Repo 3 collects jobs.json
→ Repo 2 generates recommendations.json
```

Repo 4 saves the terminal text to `outputs/profile_input.txt`, then calls Repo 1 through its file-based extraction command.

### Voice mode

Voice mode lets the user provide career preferences through the microphone.

```text
voice input
→ Repo 1 records, transcribes, and extracts career_profile.json
→ Repo 4 reads target_roles
→ Repo 3 collects jobs.json
→ Repo 2 generates recommendations.json
```

Repo 4 does not rebuild the microphone or transcription logic. It calls Repo 1 interactively and lets Repo 1 handle recording, transcription, and profile extraction.

## MVP Workflow

The expanded local MVP workflow is:

```text
user input
→ career_profile.json
→ resolved job queries
→ jobs.json
→ recommendations.json
```

Depending on the selected input mode, the first stage can start from:

- an existing profile
- terminal text
- microphone input

Repo 4 treats Repo 1, Repo 2, and Repo 3 as external CLI tools instead of importing their internal Python modules directly. This keeps the repositories loosely coupled and easier to test independently.

## Job Query Resolution

The orchestrator does not use a default job search query.

Job queries are resolved in the following order:

```text
explicit --query options provided
→ use the explicit queries

no --query options provided
→ read target_roles from career_profile.json

no explicit queries and no target_roles
→ stop with a clear error
```

This prevents the application from silently searching for an unrelated role when the user forgets to provide a query.

### Automatic queries from the career profile

When `--query` is omitted, Repo 4 reads all valid values from the `target_roles` field.

For example:

```json
{
  "target_roles": [
    "software developer",
    "backend developer",
    "data analyst"
  ]
}
```

The orchestrator passes the equivalent repeated query options to Repo 3:

```text
--query "software developer"
--query "backend developer"
--query "data analyst"
```

Repo 3 collects jobs for every query, combines the results, normalizes them, removes duplicate listings, and exports one `jobs.json` file.

### Explicit queries

The user can override profile-derived queries by providing one or more `--query` options:

```bash
--query "software developer" \
--query "backend developer"
```

When explicit queries are provided, they take priority over `target_roles` in the profile.

Queries are cleaned and deduplicated case-insensitively while preserving their original order.

For example:

```text
" software developer "
"Software Developer"
"backend developer"
```

becomes:

```text
software developer
backend developer
```

### Result limits

`--job-max-results` applies to each query.

For example:

```text
3 queries × 5 results per query
→ up to 15 raw jobs before deduplication
```

The final number of jobs may be lower if different queries return overlapping listings.

## Architecture

The orchestrator is designed around file-based workflow contracts.

The main files are:

```text
career_profile.json
jobs.json
recommendations.json
```

The orchestrator is responsible for:

- managing input and output paths
- accepting profile, text, and voice input modes
- calling Repo 1 when profile extraction is required
- resolving explicit or profile-derived job queries
- passing repeated queries to Repo 3
- calling the job collection step
- calling the recommendation step
- displaying workflow progress and resolved queries
- keeping tests independent from external APIs
- keeping tests independent from local Repo 1, Repo 2, and Repo 3 installations

The orchestrator is not responsible for:

- implementing career profile extraction logic itself
- implementing raw job collection logic itself
- implementing job scoring logic itself
- storing data in a database
- serving a web frontend or backend API

Profile extraction is delegated to Repo 1, job collection is delegated to Repo 3, and recommendation scoring is delegated to Repo 2.

Repo 3 uses the Adzuna API. Repo 4 therefore needs access to the same Adzuna environment variables when it runs job collection.

Create a local `.env` file:

```bash
touch .env
```

Add:

```env
ADZUNA_APP_ID=your_app_id_here
ADZUNA_APP_KEY=your_app_key_here
ADZUNA_COUNTRY=au
```

Do not commit `.env` to GitHub.

The repository's `.gitignore` excludes `.env`.

### Optional OpenAI configuration

LLM-assisted profile extraction or recommendation scoring requires OpenAI API configuration.

These options require LLM access:

```text
--profile-extractor llm
--scorer llm
```

Add the required OpenAI API key according to the Repo 1 and Repo 2 setup instructions.

For example:

```env
OPENAI_API_KEY=your_openai_api_key_here
```

OpenAI API usage may require separate API billing. A ChatGPT subscription does not automatically include OpenAI API credits.

## Run the Orchestrator

The orchestrator supports three input modes.

### Option 1: Existing Profile Mode

Use this mode when you already have a `career_profile.json`.

```bash
uv run careervoice-run \
  --input-mode profile \
  --profile examples/career_profile.json \
  --source adzuna \
  --location Adelaide \
  --job-max-results 10 \
  --recommendation-max-results 5 \
  --scorer rules \
  --jobs-output outputs/jobs.json \
  --recommendations-output outputs/recommendations.json \
  --verbose
```

Because no `--query` option is provided, the orchestrator reads all valid roles from `target_roles` in `examples/career_profile.json`.

This runs:

```text
existing career_profile.json
→ resolve target_roles
→ job-collect with repeated queries
→ job-recommend
```

### Option 2: Terminal Text Input Mode

Use this mode when you want to type career preferences directly into the terminal.

```bash
uv run careervoice-run \
  --input-mode text \
  --profile outputs/career_profile.json \
  --profile-extractor rules \
  --source adzuna \
  --location Adelaide \
  --job-max-results 10 \
  --recommendation-max-results 5 \
  --scorer rules \
  --jobs-output outputs/jobs.json \
  --recommendations-output outputs/recommendations.json \
  --verbose
```

The terminal asks for career preference text:

```text
Please enter your career preference.
Press Enter on an empty line when finished:
```

Example input:

```text
I want a software developer, backend developer, or data analyst role in Adelaide.
I know Python, SQL, Git, and React.
I prefer backend development, software engineering, data-related roles, and AI tools.
I want to avoid sales, customer service, and senior roles.
```

Press Enter on an empty line to finish.

This runs:

```text
terminal text input
→ Repo 1 creates career_profile.json
→ Repo 4 reads target_roles
→ Repo 3 creates jobs.json
→ Repo 2 creates recommendations.json
```

After Repo 1 generates the profile, Repo 4 reads its `target_roles` and uses them as job collection queries.

### Option 3: Voice Input Mode

Use this mode when you want to provide career preferences through the microphone.

```bash
uv run careervoice-run \
  --input-mode voice \
  --profile outputs/career_profile.voice-test.json \
  --profile-extractor rules \
  --source adzuna \
  --location Adelaide \
  --job-max-results 5 \
  --recommendation-max-results 3 \
  --scorer rules \
  --jobs-output outputs/jobs.voice-test.json \
  --recommendations-output outputs/recommendations.voice-test.json \
  --verbose
```

Repo 1 handles recording, transcription, and profile extraction.

This runs:

```text
voice input
→ Repo 1 creates career_profile.json
→ Repo 4 reads target_roles
→ Repo 3 creates jobs.json
→ Repo 2 creates recommendations.json
```

After Repo 1 creates the profile, Repo 4 reads the extracted `target_roles` and passes them to Repo 3.

```bash
uv run careervoice-run \

  --profile examples/career_profile.json \
  --source adzuna \
  --query "software developer" \
  --query "backend developer" \
```

In this example, the explicit queries override the roles stored in the career profile.

## Rules Scorer vs LLM Scorer

The recommender supports two scoring modes:

```text
--scorer rules
--scorer llm
```

### Rule-based scorer

The rule-based scorer is the default option.

```bash
uv run job-recommend \
  --profile outputs/career_profile.json \
  --jobs outputs/jobs.json \
  --max-results 5 \
  --scorer rules \
  --output outputs/recommendations.rules.json
```

Advantages:

- fast
- deterministic
- works without an OpenAI API key
- easier to test
- predictable across repeated runs

Limitations:

- stricter keyword matching
- weaker semantic understanding
- may not fully understand relationships between similar job titles

For example, these titles may require additional matching rules:

```text
software developer
software engineer
full stack developer
junior software developer
```

### LLM-assisted scorer

The LLM scorer provides more flexible semantic matching and richer explanations.

```bash
uv run job-recommend \
  --profile outputs/career_profile.json \
  --jobs outputs/jobs.json \
  --max-results 5 \
  --scorer llm \
  --output outputs/recommendations.llm.json
```

Advantages:

- better semantic matching
- richer explanations
- better handling of incomplete job descriptions
- better recognition of related job titles and skills

Limitations:

- requires OpenAI API configuration
- may use paid API credits
- results may vary slightly between runs
- is slower than rule-based scoring

For local MVP testing, `rules` is the safest default. For richer semantic matching, `llm` usually produces stronger results.

## CLI Options

```text
--input-mode
    Input mode. Supports profile, text, and voice.
    Default: profile.

--profile-input
    Path where terminal text input is saved before Repo 1 reads it.

--profile
    Path to career_profile.json.

    In profile mode, this is an existing input file.
    In text or voice mode, this is the profile output generated by Repo 1.

--profile-extractor
    Profile extractor used by Repo 1.
    Supports rules and llm.
    Default: rules.

--jobs-output
    Path where collected jobs.json is saved.

--recommendations-output
    Path where recommendations.json is saved.

--source
    Job listing source.
    Currently supports adzuna.
    Default: adzuna.

--query
    Optional job search query.

    Repeat this option to provide multiple queries.
    When omitted, target_roles are read from the career profile.
    Explicit queries override profile-derived queries.
    There is no default job role.

--location
    Job search location.
    Use an empty string for no location.
    Default: Adelaide.

--job-max-results
    Maximum number of jobs to collect for each query.
    Default: 10.

--recommendation-max-results
    Maximum number of ranked recommendations to return.
    Default: 10.

--scorer
    Recommendation scorer used by Repo 2.
    Supports rules and llm.
    Default: rules.

--exclude-rejected
    Exclude jobs rejected by hard constraints.

--verbose
    Show output captured from external repository commands.
```

Check all options:

```bash
uv run careervoice-run --help
```

## Current Limitations

The current MVP has the following limitations:

- It is a local CLI workflow only.
- It depends on the other three repositories being installed locally.
- Voice input depends on local microphone access and Repo 1's optional voice dependencies.
- Job collection depends on the Adzuna API.
- LLM-assisted extraction or scoring requires OpenAI API configuration.
- Automatic job queries are taken directly from `target_roles`; the orchestrator does not yet prioritize, rewrite, or semantically optimize them.
- `--job-max-results` applies to every query, so profiles with many target roles may cause more Adzuna API requests.
- The job location is still supplied through the CLI and is not automatically derived from the career profile.
- It does not include Docker.
- It does not include a web app or backend API.
- It does not include scheduled job collection.
- It does not include production deployment.

### Automatic multiple-query collection

For every workflow mode, Repo 4 can now:

```text
read multiple target_roles
→ pass repeated queries to Repo 3
→ combine collected listings
→ deduplicate overlapping jobs
→ run recommendation scoring once
```

Users may also provide repeated `--query` options to override profile-derived roles.

- file-based data contracts
- subprocess-based integration
- automatic query resolution
- repeated query handling
